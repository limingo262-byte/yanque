> - Python：`YanQue-AI-14/src/yanque_ai/modules/knowledge`  
> - 学生端问答（是否 RAG）：`aichat`（Java）+ `chat`（Python）

## 1. 总体架构

```
┌─────────────────┐     HTTP/SSE      ┌──────────────────┐     HTTP/SSE      ┌─────────────────┐
│  管理端 / 学生端  │ ───────────────► │  Java Admin 服务  │ ───────────────► │  Python AI 服务  │
│  (仅调 Java API) │                  │  MySQL 业务数据   │                  │  Milvus + 模型   │
└─────────────────┘                  └──────────────────┘                  └────────┬────────┘
                                                                                    │
                                                                           ┌────────▼────────┐
                                                                           │     Milvus      │
                                                                           │ dense + BM25    │
                                                                           └─────────────────┘
```

| 层级 | 职责 |
|------|------|
| **Java** | 知识库/文档元数据（MySQL）、权限与状态校验、TOS 预签名、转发 Python、SSE 透传给前端 |
| **Python** | Milvus Collection 管理、Markdown 切分与向量入库、召回检索、RAG 拼 prompt、调用百炼模型流式生成 |
| **Milvus** | 每个知识库一个 Collection（名称 = 知识库 `code`），存 chunk 文本 + 稠密向量 + BM25 稀疏向量 |

**分工原则**：Java 不碰向量与 LLM；Python 不碰 MySQL 业务表。两边通过内部 HTTP（`yanque-ai.base-url`，默认 `http://localhost:8000`）通信。

## 2. 创建知识库之后，召回/问答能跑的前提

召回测试和知识问答都依赖：**库已 ACTIVE + Collection 已建 + 文档已入库 READY**。

### 2.1 创建知识库

| 步骤 | 位置 | 做什么 |
|------|------|--------|
| 1 | Java `AiKnowledgeBaseController` `POST /api/ai/knowledge-bases` | 入参：name / code / description |
| 2 | Java `AiKnowledgeBaseServiceImpl.create` | 先写 MySQL（状态 `ACTIVE`，文档/分段数 0） |
| 3 | Java `initVectorCollection` → `AiKnowledgePythonClient.createKnowledgeBaseCollection` | `POST {python}/ai/knowledge-bases/create` |
| 4 | Python `KnowledgeService.create_knowledge_base` | `build_collection_name(code)` → Milvus 建表 |
| 5 | 失败补偿 | Python/Milvus 失败 → Java 删除刚插入的 MySQL 记录 |

**Milvus Schema 要点**（`vector_store.py`）：

| 字段 | 说明 |
|------|------|
| `id` | 主键，如 `{document_code}_v{version}_{chunk_index}` |
| `document_code` / `document_version` / `chunk_index` | 业务定位 |
| `text` | chunk 原文，开中文 analyzer，供 BM25 |
| `dense_vector` | 稠密向量（百炼 embedding，默认 dim=1024，COSINE） |
| `sparse_vector` | BM25 稀疏向量（Function 从 `text` 自动生成） |

### 2.2 文档入库（知识列表有数据后）

| 步骤 | 位置 | 做什么 |
|------|------|--------|
| 1 | Java 预签名上传 | TOS 上传 `.md` |
| 2 | Java `AiKnowledgeDocumentServiceImpl.create` | MySQL 插文档，`status=INDEXING`，异步 `submitIndexTask` |
| 3 | 后台 `indexDocument` | TOS 预签名下载 URL → Python `POST /ai/knowledge-bases/documents/index` |
| 4 | Python `index_knowledge_document` | 下载 Markdown → LlamaIndex `MarkdownNodeParser` 切分 → embedding → insert Milvus |
| 5 | Java 回写 | 成功 `markReady` + chunk_count；失败 `markFailed`；刷新库统计 |

只有文档 `READY` 后，召回/问答才有有效 chunk。

## 3. 管理端：召回测试（完整流程）

### 3.1 接口

- **对外（管理端调 Java）**  
  `POST /api/ai/knowledge-bases/{id}/recall`
- **内部（Java 调 Python）**  
  `POST /ai/knowledge-bases/recall`

### 3.2 请求参数

| 字段 | 默认 | 说明 |
|------|------|------|
| `query` | 必填 | 检索文本 |
| `mode` | `HYBRID` | `SEMANTIC` / `KEYWORD` / `HYBRID` |
| `topK` | `5` | 范围 1~20 |

### 3.3 Java 流程

```
Controller.recall(id, req)
  → BaseServiceImpl.recall
       1. require(id) 查库，不存在抛 KNOWLEDGE_BASE_NOT_FOUND
       2. 状态必须 ACTIVE，否则 KNOWLEDGE_BASE_STATUS_INVALID
       3. 规范化 mode（仅 SEMANTIC/KEYWORD/HYBRID）、trim query、topK 默认 5
       4. pythonClient.recallKnowledgeBase(entity, req)
  → 返回 ApiResponse<AiKnowledgeRecallRes>
```

`AiKnowledgePythonClient.recallKnowledgeBase` 组装 snake_case body：

```json
{
  "knowledge_base_code": "<code>",
  "query": "...",
  "mode": "HYBRID",
  "top_k": 5
}
```

把 Python 响应映射为 `AiKnowledgeRecallRes`（query / mode / topK / records）。

### 3.4 Python 流程

```
router.recall_knowledge_base
  → KnowledgeService.recall_knowledge_base
       collection = build_collection_name(code)   # 一般就是 code 本身
       records = vector_store.recall(collection, query, mode, top_k)
  → KnowledgeRecallResponse
```

### 3.5 Milvus 三种召回模式（`KnowledgeVectorStore.recall`）

| mode | 实现 | 说明 |
|------|------|------|
| **SEMANTIC** | `_semantic_search` | query → embedding → `dense_vector` ANN（COSINE） |
| **KEYWORD** | `_keyword_search` | 原文 query → `sparse_vector` BM25 检索 |
| **HYBRID** | `_hybrid_search` | dense + sparse 双路 `hybrid_search`，`WeightedRanker(0.7, 0.3)` |

命中结果转为：

```text
rank, score, document_code, document_version, chunk_index,
content, content_preview, word_count
```

**注意**：召回测试只做检索，**不调用大模型**。

## 4. 管理端：知识问答（完整流程，RAG）

### 4.1 接口

- **对外**  
  `POST /api/ai/knowledge-bases/{id}/qa/stream`  
  `Content-Type: application/json`，响应 `text/event-stream`
- **内部**  
  `POST /ai/knowledge-bases/qa/stream`（SSE）

### 4.2 请求参数

| 字段 | 默认 | 说明 |
|------|------|------|
| `question` | 必填 | 问题，最长 1000 |
| `recallMode` | `HYBRID` | 与召回测试相同三模式 |
| `topK` | `5` | 1~20 |

### 4.3 Java 流程

```
Controller.qa(id, req)  →  ResponseEntity.ok(SseEmitter)
  → BaseServiceImpl.qa
       1. 校验库存在且 ACTIVE
       2. 规范化 recallMode / question / topK
       3. new SseEmitter(0L)  // 不超时
       4. new Thread(() -> streamQa(...)).start()  // 避免阻塞 Tomcat 请求线程
  → streamQa
       pythonClient.streamKnowledgeBaseQa(..., event -> {
           sendEvent(emitter, event.name, event.data)  // 原样转发
           done/error 时 emitter.complete()
       })
```

Java **不做业务拼装**，只做：校验 → 调 Python SSE → 按行解析 `event:` / `data:` → 转发给浏览器。

### 4.4 Python RAG 流程（核心）

`KnowledgeService.stream_knowledge_base_qa`：

```
1. collection = build_collection_name(knowledge_base_code)
2. citations = vector_store.recall(collection, question, recall_mode, top_k)
3. SSE event=citations  →  先把引用分段推给前端
4. 若 citations 为空：
     SSE delta: 「知识库中未找到足够依据…」
     SSE done: finish_reason=no_citations
     return
5. 有 citations：
     messages = _build_qa_messages(question, citations)
     BailianClient.stream_chat(messages)
       → 每个 token: SSE delta { content }
       → 结束: SSE done { model, finish_reason, truncated, usage }
6. 异常: SSE error { code, message }
```

### 4.5 RAG Prompt 怎么拼

`_build_qa_messages`：

- **system**：管理后台知识库问答测试助手；**只能基于引用分段回答**；依据不足要明确说明。
- **user**：

```text
问题：{question}

引用分段：
[1] 文档编码：xxx，chunk：n
{content}
...

请基于引用分段给出答案。
```

这是标准 **Retrieve → Augment prompt → Generate** 的 RAG。

### 4.6 SSE 事件约定

| event | 含义 | data 要点 |
|-------|------|-----------|
| `citations` | 召回引用列表 | `{ "citations": [ {...}, ... ] }` |
| `delta` | 回答增量 | `{ "content": "..." }` |
| `done` | 正常结束 | model / finish_reason / usage 等 |
| `error` | 失败 | code / message |

## 7. 学生端问答是否实现了 RAG？

### 结论：**实现了。**

学生端走的是 **聊天模块**，不是管理端 `aiknowledge` 的 `/{id}/qa/stream`，但底层共用同一套 `KnowledgeVectorStore.recall`。

### 7.1 代码位置

| 端 | 路径 |
|----|------|
| Java 学生会话 | `cn.yanque.modules.aichat`（`AiChatController` / `AiChatService` / `AiServiceClient`） |
| Python 编排 | `yanque_ai.modules.chat.service.ChatService` |
| Prompt | `yanque_ai.modules.chat.prompts` |
| 向量检索 | `yanque_ai.modules.knowledge.vector_store.KnowledgeVectorStore`（复用） |

### 7.2 学生端调用链

```
学生前端
  → Java POST .../messages/stream（AiChatService.send）
       建/复用会话、落库 user 消息、历史上下文
       AiServiceClient.streamChat → Python POST /ai/chat/stream
  → Python ChatService.stream_chat
       _messages(request)
         └─ _recall_qa_context(question)   ← RAG 入口
              if chat_rag_enabled:
                  vector_store.recall(固定 collection, mode, recall_top_k)
                  可选 qwen3-rerank 重排 + 分数阈值过滤
              else:
                  citations = None  → 不拼知识库
         └─ build_messages(..., citations=...)
       BailianClient.stream_chat → SSE delta/done
  → Java 转发 SSE，done 时落库 assistant 消息，并可能触发摘要压缩
```

### 7.3 配置（`common/config.py`，环境变量）

| 配置项 | 环境变量 | 默认 |
|--------|----------|------|
| 是否开启 RAG | `AI_CHAT_RAG_ENABLED` | `True` |
| 固定 Collection | `AI_CHAT_RAG_COLLECTION` | `student_qa` |
| 召回模式 | `AI_CHAT_RAG_RECALL_MODE` | `HYBRID` |
| 入模 top_k | `AI_CHAT_RAG_TOP_K` | `5` |
| 重排前召回量 | `AI_CHAT_RAG_RECALL_TOP_K` | `20` |
| 是否重排 | `AI_CHAT_RAG_RERANK_ENABLED` | `True` |
| 重排模型 | `AI_CHAT_RAG_RERANK_MODEL` | `qwen3-rerank` |
| 重排最低分 | `AI_CHAT_RAG_RERANK_MIN_SCORE` | `0.6` |

### 7.4 管理端知识问答 vs 学生端 RAG

| 对比项 | 管理端知识问答 | 学生端聊天 RAG |
|--------|----------------|----------------|
| 入口 | `aiknowledge` `/{id}/qa/stream` | `aichat` + `/ai/chat/stream` |
| Collection | 按知识库 `code` 动态指定 | 配置里的**固定**集合（默认 `student_qa`） |
| 多轮历史 | 无（单次测试） | 有（history + summary） |
| 重排 Rerank | **无** | **有**（可选，失败则用原始召回顺序） |
| 无召回结果 | 直接说无法回答，不强行通用发挥 | 提示无知识库依据，仍可用通用学习助教能力回答 |
| 召回失败 | SSE error | **降级普通问答**（citations=None，不阻塞聊天） |
| 先推 citations 事件 | **有** | **无**（引用只进 prompt，不单独推前端事件） |
| 会话落库 | 无 | 有（session/message + 压缩） |

### 7.5 学生端 RAG 策略摘要

1. `chat_rag_enabled=false` → 完全不查库，普通 LLM 对话。  
2. enabled → 在配置的 Collection 上 `recall`（默认 HYBRID）。  
3. 若开启 rerank → 用 `qwen3-rerank` 对候选 chunk 打分，过滤低于 `min_score` 的，取 top_k。  
4. 将引用写入 user 消息中的 `【QA知识库参考资料】`，约束模型优先依据资料作答。  
5. 召回异常只打日志并降级，保证学生端可用性。

## 9. 流程一句话总结

1. **建库**：Java 写 MySQL → Python 建 Milvus Collection。  
2. **灌文档**：Java 记元数据 + TOS → Python 切分/向量化写入该 Collection。  
3. **召回测试**：Java 校验 ACTIVE → Python 按 SEMANTIC/KEYWORD/HYBRID 查 topK chunk → JSON 返回。  
4. **管理端知识问答**：在召回基础上拼 RAG prompt → 百炼流式回答 → SSE（citations → delta → done）。  
5. **学生端问答**：**已实现 RAG**；复用同一向量检索能力，但使用固定 QA Collection，并可做 Rerank；失败可降级为普通对话。

## 10. Python 返回方式澄清（复习重点）

常见会误以为有两种「流式」；结合代码，准确说法如下。

### 10.1 两种理解 vs 实际行为

| # | 说法 | 是否正确 | 实际是什么 |
|---|------|----------|------------|
| 1 | 先把检索到的信息**流式**返回 | **半对** | 会**先**返回检索结果，但是 **一整包**（一次 `citations` 事件），**不是**边检索边一条条流式吐出 |
| 2 | 把 RAG 上下文交给大模型，再**流式**返回答案 | **对** | 引用齐了才调模型；**只有模型输出**是 token 级流式（`delta`） |

**一句话**：  
`检索 = 同步整包` → `引用 = 单次 SSE 推送` → `回答 = 大模型流式 SSE`。

### 10.2 管理端知识问答：Python 到底回了什么

入口：`KnowledgeService.stream_knowledge_base_qa`  
路径：`POST /ai/knowledge-bases/qa/stream`

| 阶段 | 流式？ | 做什么 | SSE |
|------|--------|--------|-----|
| A. 检索 | **否** | `vector_store.recall(...)` 一次取完 top_k | 无 |
| B. 推引用 | **否（单次事件）** | 把完整 citations 列表推给前端 | `event: citations` |
| C. 无引用短路 | 固定文案一次 | 不调大模型 | `delta` + `done(no_citations)` |
| D. 有引用 → 生成 | **是** | 拼 prompt → 百炼 `stream_chat` | 多次 `delta` → `done` |
| E. 异常 | 单次 | 召回失败 / 模型失败 | `event: error` |

### 10.3 逐步流程（对照代码，便于背）

```text
1. collection = build_collection_name(knowledge_base_code)
   → 知识库 code 变成 Milvus 表名，后续都查这张表

2. citations = vector_store.recall(collection, question, recall_mode, top_k)
   → 【检索 / 召回】用问题在向量库找最相关的 chunk
   → 输入：问题 + 模式(SEMANTIC/KEYWORD/HYBRID) + top_k
   → 输出：citations 列表（文档编码、chunk 序号、原文、分数…）
   → 此步不调大模型，同步整包完成（不是流式检索）

3. yield SSE event=citations  { citations: [...] }
   → 先把引用整包推给前端，页面可先展示「引用依据」
   → 注意：是「先推一次完整列表」，不是检索过程的流式

4. 若 citations 为空：
     yield delta  「知识库中未找到足够依据…」
     yield done   finish_reason=no_citations
     return
   → 没依据就不编造，不进大模型

5. 有 citations：
     messages = _build_qa_messages(question, citations)
       → system：只能依据引用回答
       → user：问题 + 全部引用分段原文
     BailianClient.stream_chat(messages)
       → 每个 token：SSE delta { content }
       → 结束：    SSE done  { model, finish_reason, truncated, usage }
   → 【真正流式的部分】只有大模型答案

6. 异常：
     yield error { code, message }
```

### 10.4 时序示意（管理端）

```text
时间 ──────────────────────────────────────────────────────────►

[recall 同步]  ──►  [citations 一次]  ──►  [LLM delta…][delta…][done]
   整包 chunk          整包引用推前端         只有答案在流式
```

前端收到的顺序：

```text
event: citations   ← 引用（整包，1 次）
data: {"citations":[...]}

event: delta       ← 答案片段（多次）
data: {"content":"..."}

event: delta
data: {"content":"..."}

event: done        ← 结束（1 次）
data: {"model":"...","finish_reason":"...","usage":...}
```

### 10.5 和「召回测试」对比（别混）

| 接口 | 检索 | 大模型 | 返回形态 |
|------|------|--------|----------|
| `POST .../recall` 召回测试 | 有 | **无** | 普通 JSON，一次返回 records |
| `POST .../qa/stream` 知识问答 | 有 | **有** | SSE：先 citations，再 delta 流式答案 |

### 10.6 学生端差异（复习时别和自己绕晕）

学生端 `ChatService.stream_chat`：

- 同样先 `recall`（可再 Rerank），**检索仍是同步整包**  
- **不**单独推 `citations` SSE  
- 引用只塞进 prompt，前端只看到 `delta` / `done`  
- 所以学生端「看起来只有一种流式」——答案流式；引用对用户不可见（除非以后加）

## 12. 面试话术（可直接说）

### 12.1 开场 30 秒（项目介绍）

> 「我做的是教育场景的知识库模块。管理端可以建知识库、上传 Markdown、做召回测试和知识问答。架构上 Java 负责业务元数据和权限，Python 负责切分、Milvus 向量检索和调大模型。知识问答是标准 RAG：先召回 chunk，再拼进 prompt 流式生成；前后端用 SSE 推送。」

### 12.2 若问：你们 RAG 怎么做的？

> 「分三步。  
> 第一，入库：Markdown 用 LlamaIndex 按标题切 chunk，百炼 embedding 写 dense 向量，Milvus 对 text 做中文分词自动生成 BM25 sparse。  
> 第二，检索：支持语义、关键字、混合三种 mode，混合是 dense 0.7 + sparse 0.3。  
> 第三，生成：把 topK 引用和问题拼成 prompt，约束模型只能依据引用回答；答案走百炼 stream，前端 SSE 展示。  
> 管理端会先推一条 citations 事件，再推 delta；学生端复用同一套 recall，可选 rerank，失败降级普通聊天。」

### 12.3 若问：为什么 Java 还要 Python？

> 「职责拆分。Java 更适合权限、事务、MySQL、对象存储预签名；向量库、embedding、BM25、流式调模型这些 AI 链路放 Python 更合适。两边用内部 HTTP，Java 不直接连模型，Python 不写业务表。」

### 12.4 若问：流式是怎么做的？delta 是什么？

> 「Spring 用 `SseEmitter(0L)`，0 表示不超时，因为生成可能较久。Java 开后台线程调 Python 的 SSE，解析 `event/data` 后原样转给浏览器。  
> Python 里百炼 `stream_chat` 按 chunk 读上游，有文本就 yield 一个 `StreamChunk(delta)`，上层转成 `event:delta`。  
> **delta 就是大模型流式输出的一小段新增文本**，多次 delta 拼成完整答案，最后再发 done。」

### 12.5 若问：检索是不是也流式？

> 「不是。容易混淆。  
> 检索是同步整包：`recall` 一次返回 topK。  
> 管理端问答会把 citations **整包推一次**（看起来像‘先返回检索结果’，但不是边检索边流）。  
> **真正流式的只有大模型答案。**  
> 口诀：检索不流式，引用推一次，答案才流式。」

### 12.6 若问：混合检索怎么做？

> 「Milvus hybrid_search，一路 dense 语义，一路 BM25 sparse，WeightedRanker 权重 0.7 和 0.3。语义补近义词，关键字补专有名词和制度条文，混合更稳。」

### 12.7 若问：没有召回结果怎么办？

> 「管理端：直接固定回复‘未找到足够依据’，finish_reason=no_citations，不调模型，避免幻觉。  
> 学生端：prompt 里说明未检索到依据，仍可用通用助教能力给学习建议，且召回异常会降级，不把聊天整条打挂。」

### 12.8 若问：SseEmitter(0L) 是什么？

> 「Spring 的服务端推送对象，用来发 SSE。构造参数是超时毫秒数，传 0 表示不超时，适合长耗时问答流；业务上在 done 或 error 时 `complete()` 关掉连接。」

### 12.9 若问：学生端和管理端有何不同？

| 点 | 管理端 QA | 学生端 Chat |
|----|-----------|-------------|
| Collection | 按知识库 code | 配置固定集（如 student_qa） |
| citations SSE | 有 | 无（只进 prompt） |
| Rerank | 无 | 可选 qwen3-rerank |
| 多轮 | 无 | history + summary |
| 失败 | 报错 | 可降级普通对话 |

> 口述：「同一套向量检索能力，产品形态不同：管理端是调试台，学生端是带会话的助教。」

### 12.10 若问：前端收不到流式结果可能啥问题？（踩过的坑）

> 「我们遇过 SSE 解析过严：前端写死 `data: ` 冒号后必须有空格，而 Spring 发的是 `data:{...}` 无空格，事件全丢。修复是兼容有无空格，并支持 `\r\n`。这类问题后端有日志、前端空白，优先抓 Network 里原始 SSE 文本。」

### 12.11 若问：如何保证答案不瞎编？

> 「prompt 硬约束：只能基于引用；依据不足要明确说找不到。管理端无引用直接不调模型。入库只收业务文档，检索 topK 可控。学生端还有 rerank 阈值过滤低相关片段。」
