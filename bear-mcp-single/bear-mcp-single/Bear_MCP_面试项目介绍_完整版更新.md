## 零、今天面试先讲这一部分

这一部分是最新项目介绍。面试时先讲这里，再根据面试官的问题进入后面的详细模块。

### 1. 20 秒介绍

我做的是一个面向 AI Agent 的企业 MCP 能力治理平台。它把内部 API、数据库、文档，以及飞书等外部 MCP 工具统一接入，并负责权限、动态发布和调用审计。这样 Cursor、Codex 或自研 Agent 只接一个入口，就能安全使用多套企业能力。

### 2. 1 分钟介绍

公司内部已经有很多业务 API、数据库和文档，外部也有飞书等 MCP 服务，但这些能力比较分散。如果每个 Agent 分别接入，不但会重复开发，而且鉴权、权限和审计也不好统一。

所以我基于 MCP 协议做了 Bear MCP 统一入口。一方面，它可以把 HTTP API、数据库查询、Prompt、Resource 和 Skill 封装成 Agent 能理解的能力；另一方面，它也可以代理飞书官方远程 MCP，让 Bear 不只提供自己的工具，还能聚合其他 MCP Server 的工具。

我主要完成了动态工具发布、角色和 Token 双层权限、外部 MCP 接入、工具编排、Prompt 和 Resource 扩展、能力社区以及全链路审计。最终 Agent 只连接 Bear MCP，就可以在权限范围内使用多个系统的能力。

### 3. 3 分钟介绍

这个项目叫 Bear MCP，是一个面向企业 AI Agent 的能力接入和治理平台。

它主要解决三个问题。

第一，企业能力比较分散。订单、支付、日志等能力可能是 HTTP API，业务数据在数据库里，知识在文档里，飞书又提供了自己的远程 MCP。每个 Agent 单独对接一次，成本很高。

第二，AI 不能看到所有工具。不同用户、不同客户端和不同环境可以使用的能力应该不同，而且每次调用都必须能够追踪。

第三，普通 MCP 工具经常写死在代码里。新增一个工具需要开发、编译、发布和重启，不适合企业能力快速变化的场景。

我的做法是把 Bear MCP 建成统一能力入口。内部能力可以通过 HTTP API、只读数据源、动态 Tool、Prompt、Resource 和 Skill 接入；外部能力可以通过远程 MCP 接进来。目前已经接入飞书官方 MCP，可以发现和调用飞书工具，完成文档搜索、读取、创建和评论等操作。

治理方面，我做了角色权限和 Token 工具选择两层控制。角色决定用户最多能用什么，Token 决定某个 Agent 本次实际暴露什么。工具列表会过滤，真正调用时还会再次校验，避免客户端绕过列表直接调用。每次调用都会记录结果、耗时和调用人，方便审计和排查。

扩展方面，能力作者可以先接入 API，再把它编排成动态工具，调试后发布，不需要每次修改主服务。外部 MCP 接入以后，Bear 也从单个 MCP Server 升级成了 MCP 聚合和治理入口。

这个项目的价值不是多做几个工具，而是把分散能力变成一个可发现、可调用、可控制、可审计、可复用的平台。

### 4. 项目背景怎么说

最简单的说法：**公司不是没有能力，而是能力太分散，AI 不知道怎么统一、安全地使用。**

原来的问题主要有：

1. 每个 Agent 都要分别接订单、日志、数据库和飞书，存在重复开发。
2. API、数据库、文档和外部 MCP 的接入方式不同，使用成本高。
3. 工具写死在代码里，新增能力需要重新发版。
4. 所有用户看到同一批工具，存在越权风险。
5. 调用失败后，不知道是谁在什么时间调用了什么。
6. 飞书等平台即使已经提供 MCP，每个客户端分别配置后，凭证和权限仍然分散。

一句话价值：**Bear MCP 把分散的企业能力统一包装和治理，让 AI Agent 接一次就能按权限使用。**

### 5. 我做了哪些功能

1. **统一 MCP 入口**：Cursor、Codex 和自研 Agent 只需要连接 Bear。
2. **动态工具**：把已有 API 包装成 Tool，调试和发布后即可被 Agent 使用。
3. **外部能力接入**：支持 HTTP API、只读数据源和飞书远程 MCP。
4. **双层权限**：角色决定能力上限，Token 决定当前客户端实际开放范围。
5. **完整 MCP 能力**：管理和使用 Tool、Prompt、Resource 与 Skill。
6. **能力社区**：团队可以发布和复用已有能力，减少重复建设。
7. **调用审计**：记录调用人、Token、能力、结果和耗时。
8. **外部 MCP 聚合**：Bear 对上是 MCP Server，对下也能作为 MCP Client 调用其他 MCP。

### 6. 新增的飞书远程 MCP

Bear 现在不仅提供自己的工具，还可以向下代理飞书官方远程 MCP，再把飞书能力统一提供给上层 Agent。

当前已经实现的飞书能力包括：

- 查询飞书官方 MCP 当前提供的工具。
- 通用调用指定飞书 MCP 工具。
- 搜索飞书云文档。
- 读取飞书云文档。
- 创建飞书云文档。
- 给飞书文档添加评论。

最简单的介绍是：**MCP Server 后面还能再接 MCP Server，Bear 负责统一入口和治理。**

面试时必须说准确：当前实际落地的是飞书。企业微信是同类扩展方向，不要说成已经完成。

如果企业微信提供标准 MCP 服务，就按照远程 MCP 的方式接入；如果只提供普通 API，就先作为 HTTP API 接入，再包装成动态 Tool。

### 7. 这个项目怎么提效

这里的提效不是简单地说“AI 回答更快”，而是减少接入、开发、发布、配置和排查中的重复工作。

#### 接入提效

以前每个 Agent 分别接订单、日志、数据库和飞书。现在 Agent 只连接 Bear MCP，一个入口就能使用多种能力。

#### 开发提效

以前新增工具要写代码、测试、发版和重启。现在已有 API 可以通过平台编排成动态工具，调试后直接发布。

#### 外部 MCP 配置提效

以前每个客户端都要单独配置飞书 MCP 和凭证。现在 Bear 统一代理外部 MCP，上层 Agent 不需要分别理解不同平台的连接细节。

#### 权限提效

以前每个工具单独处理权限。现在平台通过角色和 Token 统一管理，规则集中、结果一致。

#### 团队复用提效

一个人做好的 Tool、Prompt、Resource 或 Skill，可以发布到社区让其他人复用。

#### 排障提效

审计记录包含调用对象、结果和耗时。失败时可以先查看平台记录，不需要在多个系统之间盲目查找。

一个完整例子：

> 用户说“读取飞书里的退款规范，再查询订单 1001 的退款状态”。Agent 先通过 Bear 调用飞书 MCP 读取文档，再调用内部订单或退款工具查询业务数据，最后综合回答。用户只描述一次任务，不需要打开多个系统查找和复制信息。

### 8. 最新项目亮点

#### 亮点一：从提供工具升级为聚合 MCP

普通 MCP Server 只提供自己的工具。Bear 既能提供内部工具，也能向下调用飞书等外部 MCP，再统一提供给上层 Agent。

#### 亮点二：动态发布工具

工具不完全写死在代码里，可以在平台中创建、调试、发布和下线，降低新增能力的成本。

#### 亮点三：角色和 Token 双层权限

角色权限是用户能力上限，Token 是某个客户端实际开放范围，最终可用能力是两者的交集。

#### 亮点四：发现和调用都校验

工具列表过滤只是控制“能看见什么”，真正调用时还会再次判断“能不能执行”。客户端即使直接构造调用请求，也不能绕过权限。

#### 亮点五：能力生命周期闭环

项目覆盖接入、创作、调试、发布、授权、调用、分享和审计，不只是做了几个演示工具。

#### 亮点六：面向真实客户端兼容

不同 MCP 客户端对 Prompt 和 Resource 的支持程度不完全一致，项目提供了兼容方式，让能力能够在现有客户端中真正使用。

### 9. 最新演示路线

1. 展示角色和 Token 配置，说明双层权限。
2. 用 MCP 客户端连接 Bear，查看授权后的工具列表。
3. 调用一个内部 API 或数据查询工具。
4. 调用飞书远程 MCP，搜索或读取一篇文档。
5. 回到审计页面，查看两次调用的结果和耗时。
6. 最后展示 API 接入、包装成动态 Tool、调试和发布的过程。

演示结束时说：

> Agent 只连接 Bear，但既能使用 Bear 管理的内部能力，也能使用 Bear 代理的飞书 MCP 能力；权限和审计仍然由统一入口管理。

### 10. 外部 MCP 模块怎么测试

1. 没有配置飞书凭证时，应该返回明确提示，不能出现无意义异常。
2. 凭证正确时，可以获取飞书可用工具列表。
3. 可以正常搜索、读取、创建文档并添加评论。
4. 账号没有目标文档权限时，应返回飞书侧的权限错误。
5. Bear 应限制本次允许发现和调用的飞书工具。
6. 飞书请求超时或服务不可用时，Bear 应快速失败并记录审计。
7. 飞书访问凭证不能返回给前端、Agent 或明文写入日志。
8. 外部 MCP 失败不能影响 Bear 其他内部工具的正常使用。

### 11. 面试官会怎么追问

#### Q1：为什么不让 Agent 直接调用 HTTP API？

每个 Agent 直接接 API 会重复适配，而且工具描述、参数、权限和审计都不统一。MCP 能让不同客户端按照同一个标准发现和调用工具。

#### Q2：和普通 MCP Server 有什么区别？

普通 MCP Server 一般提供固定工具。我的项目还做了动态工具、双层权限、Prompt、Resource、Skill、社区、审计和外部 MCP 聚合。

#### Q3：外部 MCP 接入解决了什么问题？

它解决了 MCP 服务本身也很分散的问题。Bear 向下连接飞书，向上只提供一个入口，减少客户端配置，并把外部能力纳入统一治理。

#### Q4：飞书 MCP 是怎么接入的？

Bear 使用服务端配置的飞书应用身份获得访问凭证，再按远程 MCP 协议完成初始化、工具发现和工具调用，最后把结果返回给上层 Agent。Agent 不需要直接处理飞书连接细节。

#### Q5：为什么使用应用身份？

应用身份适合后台服务统一调用，部署和演示比较简单。但它不等于每个用户自己的飞书权限。要严格继承用户权限，还需要增加用户 OAuth。

#### Q6：企业微信也接了吗？

目前实际落地的是飞书远程 MCP。企业微信属于同类扩展方向。如果它提供标准 MCP，就复用远程 MCP 接入流程；如果只提供普通 API，就先接 API，再包装成动态工具。

#### Q7：为什么需要角色和 Token 两层权限？

角色控制人的资格上限，Token 控制某个客户端本次开放什么。同一个人可以给开发、测试和生产创建不同 Token。

#### Q8：只过滤工具列表够安全吗？

不够。工具列表只控制看见什么，调用阶段还必须再次判断能不能执行。

#### Q9：动态工具为什么不需要每次发版？

因为工具描述、参数、执行流程以及允许使用的 API 或数据源由平台管理。发布后，客户端下次获取工具列表就能发现它。

#### Q10：外部 MCP 挂了怎么办？

Bear 应设置调用超时，返回明确的失败结果并记录审计。生产环境还要增加重试、熔断和健康检查，不能让外部服务拖垮平台。

#### Q11：Bear 会不会成为单点？

会有这个风险。生产环境需要多实例、负载均衡、共享存储、限流、熔断和监控。统一入口带来治理价值，也要求平台本身具备高可用能力。

#### Q12：如何防止飞书凭证泄露？

凭证只保存在服务端配置或密钥管理系统中，不返回给前端和 Agent；日志需要脱敏，权限尽量最小化，并定期轮换。

#### Q13：项目最难的地方是什么？

最难的不是完成一次工具调用，而是让动态工具、外部 MCP、权限和标准协议同时工作。既要让客户端正确发现工具，又要保证实际调用不能越权，还要兼容不同客户端的行为。

#### Q14：你个人做了什么？

我完成了 MCP 统一入口、动态工具、外部 API 和数据源接入、角色与 Token 双层权限、Prompt、Resource、Skill、能力社区、调用审计，以及飞书远程 MCP 代理接入。

#### Q15：项目还有什么不足？

当前是单体学习和演示版本。生产化还需要补充多实例、高可用、限流熔断、密钥管理、用户 OAuth、更强脚本沙箱、SQL 安全和监控告警。

## 一、先把项目定位讲清楚

### 1. 一句话介绍

Bear MCP 是一个面向企业的 MCP 能力中台，它把企业 API、数据库、知识文档和标准流程统一封装为 Agent 可发现、可调用、可授权、可审计的 AI 能力。

### 2. 它不是什么

- 它不是一个聊天机器人，也不负责大模型对话页面。
- 它不是单纯的 API 网关，因为它面向的是 Agent，需要提供工具描述、参数规范、知识资源和工作方法。
- 它不是只有几个固定 Tool 的 MCP Demo，而是一套支持能力创作、发布、授权、使用和审计的完整平台。
- 它不替代 Dify、Coze 或自研 Agent，而是作为能力供给侧，为不同 Agent 客户端提供统一的企业能力。

### 3. 它解决的核心问题

企业想让 AI 真正参与业务，至少要解决下面五个问题：

1. **连接问题**：AI 怎么按统一标准连接企业 API、数据库和知识文档。
2. **迭代问题**：新增一个业务工具，能不能不改主工程、不重新发版。
3. **权限问题**：不同用户、不同角色、不同 Token 能看到和调用什么。
4. **安全问题**：AI 能否被限制在白名单 API、只读 SQL 和已授权资源范围内。
5. **追责问题**：谁在什么时间调用了什么能力，参数、结果和耗时能否追踪。

Bear MCP 的核心答案是：

```text
企业能力资产化
    -> MCP 标准化暴露
    -> 角色和 Token 双层控制
    -> Agent 受控调用
    -> 全链路审计
```

## 二、面试开场话术

### 1. 30 秒版本

> 我做的是一个企业级 MCP 能力中台。普通 MCP Server 的工具通常写死在代码里，新增工具需要开发、发版和重启；我的项目把工具、API、Prompt、Resource 和 Skill 都做成了可治理的能力资产，可以在线创作、调试、发布和授权。运行时通过角色权限与 Token 选择共同决定 Agent 最终能看到和调用哪些能力，并对每次调用记录审计。项目还支持动态工具编排外部 HTTP API、只读数据源查询，以及基于企业语义资源的 Text-to-SQL。

### 2. 1 分钟版本

> Bear MCP 的定位是企业 AI 能力供给平台。它不是直接做聊天，而是把企业已有的 API、数据库、知识和流程封装成标准 MCP 能力，供 Cursor、自研 Agent 等客户端使用。
>
> 项目分成五个主要部分：第一是 MCP 运行网关，负责 Token 鉴权、能力发现、工具调用和审计；第二是动态 Tool，把工具从固定代码变成可在线配置的数据；第三是管理后台，治理用户、角色、Token、权限、数据源和审计；第四是创作空间与社区，支持 API、Tool、Prompt、Resource、Skill 的创作、调试、发布和复用；第五是 Text-to-SQL，把表结构、业务术语、指标口径和 SQL 执行边界拆成可治理资产。
>
> 我最想讲的三个亮点是：协议层扩展框架、角色权限与 Token 选择的双层模型、以及工具数据化之后形成的 Agent 自扩展闭环。

### 3. 3 分钟版本

> 这个项目的业务背景是，企业已经有大量 HTTP API、数据库和文档，但大模型既不知道这些能力，也不能直接安全使用。若每个 Agent 项目都各自对接一遍，会产生重复开发、权限分散、口径不一致和无法审计的问题。
>
> 所以我设计了 Bear MCP，把企业能力统一接到一个 MCP Server。底层 API 先被配置、调试和发布；上层动态 Tool 再通过参数 Schema 和脚本对这些 API 或只读数据源进行编排。对于 Agent 来说，它只看到标准的工具名称、描述和参数，不需要知道企业内部接口细节。
>
> 权限方面，我没有只做普通 RBAC，而是做了两层：角色权限决定用户能力上限，Token 选择决定某个客户端本次实际暴露哪些能力。这样不仅能防越权，还能减少进入模型上下文的工具数量，降低 Token 成本和工具误选率。
>
> 产品上，项目有管理后台、创作空间、能力社区和 MCP 运行端。能力可以经历草稿、调试、私有发布、公开发布、Token 装配、客户端调用和审计追踪的完整生命周期。除此之外，我还把 Text-to-SQL 拆成 Schema、业务术语、指标口径、Prompt、Skill 和只读 SQL Tool，而不是做一个什么都猜的万能工具。
>
> 项目当前仍是教学和面试版本。我已经识别出生产化前必须处理的凭据管理、接口授权、脚本隔离、SSRF、SQL 解析、缓存和核心链路测试覆盖等问题。这个项目的价值不只是功能数量，而是我对 Agent 能力治理、MCP 协议边界和企业安全约束的一次完整实践。

## 五、五类能力资产怎么区分

| 能力 | 解决什么问题 | 谁触发 | 典型例子 |
| --- | --- | --- | --- |
| Tool | 执行一个真实动作 | Agent 根据任务主动选择 | 查订单、算指标、调用内部 API |
| Prompt | 规定一次任务怎么做、怎么输出 | 用户或客户端选择 | 周报分析模板、Text-to-SQL 任务模板 |
| Resource | 提供只读事实和企业知识 | Agent 按需读取 | 表结构、业务术语、指标口径、制度文档 |
| Skill | 提供长期可复用的工作方法 | 安装到 Agent 环境后生效 | 作业检查、Text-to-SQL 工作步骤 |
| API 配置 | 描述企业接口如何调用 | Tool 调用，不直接作为 MCP Tool 暴露 | 订单详情 HTTP 接口 |

一句话记忆：

```text
Resource 给事实
Prompt 给本次要求
Skill 给长期方法
Tool 负责执行动作
API 配置是 Tool 背后的企业能力积木
```

## 六、不同角色怎么使用这个项目

### 1. 管理员

管理员进入管理后台，主要完成：

1. 创建和管理用户。
2. 为用户分配角色。
3. 为角色授权 Tool、Prompt 和 Resource，确定能力上限。
4. 创建或管理 MCP Token。
5. 为具体 Token 选择实际暴露的能力。
6. 维护数据源、查看已发布能力和审计日志。
7. 在风险出现时禁用 Token、用户、数据源或能力。

### 2. 能力创作者

创作者进入创作空间，主要完成：

1. 创建并调试一个企业 HTTP API 配置。
2. 创建动态 Tool，填写工具描述、参数规范和编排逻辑。
3. 为 Tool 绑定允许访问的 API 和数据源白名单。
4. 创建 Prompt、上传 Markdown Resource、上传 Skill。
5. 调试通过后选择私有发布或公开发布。

### 3. 普通使用者

普通使用者主要完成：

1. 在能力社区发现公开能力。
2. 创建不同用途的 MCP Token。
3. 为每把 Token 选择需要的 Tool、Prompt 和 Resource。
4. 将 MCP 配置安装到 Cursor 或其他 MCP Client。
5. 在 Agent 对话中使用已经授权的企业能力。

### 4. Agent / MCP Client

Agent 的工作顺序是：

```text
initialize 握手
    -> 读取 capabilities
    -> tools/list / prompts/list / resources/list
    -> 根据用户任务选择能力
    -> tools/call / prompts/get / resources/read
    -> 返回结果
```

## 七、项目如何启动和使用

### 1. 演示前准备

1. 安装 Java 17、Maven、Node.js 和 MySQL。
2. 创建 `bear_mcp_single` 数据库。
3. 导入 `docs/mysql-init.sql`。
4. 使用本地环境变量或本地配置提供数据库连接信息。
5. 不要在录屏或面试中展示真实数据库密码、JWT 密钥、对象存储密钥。

### 2. 启动后端

在项目根目录执行：

```powershell
mvn spring-boot:run
```

后端默认地址：

```text
http://localhost:8090
```

MCP 地址：

```text
http://localhost:8090/mcp
```

### 3. 启动前端

```powershell
cd admin-web
npm.cmd install
npm.cmd run dev
```

浏览器访问：

```text
http://localhost:5173
```

前端开发服务器会把 `/api` 请求代理到 `8090` 后端。

### 4. 课堂演示账号

```text
后台账号：demo-admin
后台密码：admin123
MCP Token：mcp_dev_token
```

这些只适用于本地教学演示，面试时要主动说明生产环境必须更换、禁用默认账号并轮换密钥。

### 5. MCP 最小使用流程

1. 客户端向 `/mcp` 发送 `initialize`。
2. 保存服务端返回的 `Mcp-Session-Id`。
3. 携带 Bearer Token 和会话 ID 请求 `tools/list`。
4. 选择一个可见工具发送 `tools/call`。
5. 回到审计页面检查本次调用状态、耗时和结果摘要。

注意点：

- `Accept` 建议同时包含 `application/json` 和 `text/event-stream`。
- 后续 MCP 请求要携带初始化阶段返回的会话 ID。
- 没有 Token 时，应在进入能力运行链路前被拒绝。
- `tools/list` 可见不代表可以绕过 `tools/call` 校验；调用阶段会再次鉴权。

## 八、推荐的完整产品演示路线

下面是一条 10 到 15 分钟的演示主线。不要一上来逐页介绍菜单，要围绕一个业务能力从创建到调用讲完整闭环。

### 场景：创建一个“查询课程信息”的动态 Tool

#### 第一步：介绍业务问题

> 企业已经有课程查询 HTTP API，但 Agent 不知道接口地址、Header、参数和返回结构。我们希望把它变成一个受权限控制、可被 Agent 自动发现和调用的 MCP Tool。

#### 第二步：创作并调试 API

1. 进入“创作空间 -> API 创作”。
2. 新建课程查询 API 配置。
3. 填写请求方法、地址、Header、默认参数和超时。
4. 先执行临时调试，确认接口可用。
5. 保存后再次调试，验证数据库中的配置也能执行。
6. 发布为“上架不公开”或“公开”。

要讲清楚：API 配置只是企业接口的调用方式，还不是 MCP Tool。

#### 第三步：创作动态 Tool

1. 进入“Tools 创作”。
2. 填写工具名称和面向模型的工具描述。
3. 定义入参 Schema，例如课程名称、页码和每页数量。
4. 绑定刚才的 API 白名单。
5. 编排返回结果并执行调试。
6. 发布 Tool。

要讲清楚：工具描述决定模型什么时候选它，参数 Schema 决定模型传什么，白名单决定它能访问什么。

#### 第四步：配置双层权限

1. 管理员在“角色与能力权限”中给角色授权这个 Tool。
2. 用户在“Token 与能力选择”中为某把 Token 勾选这个 Tool。
3. 解释最终能力是两层的交集。

```text
角色授权 = 能不能
Token 选择 = 这次带不带
```

#### 第五步：从 MCP Client 调用

1. 初始化 MCP 会话。
2. 调用 `tools/list`，确认新 Tool 已出现。
3. 用自然语言提问，让 Agent 选择并调用这个 Tool。
4. 展示返回结果。

#### 第六步：展示审计

1. 打开“调用审计”。
2. 查到刚才的调用记录。
3. 展示调用人、能力名、状态、耗时和结果摘要。

#### 第七步：做一次反向权限测试

1. 从 Token 选择中取消该 Tool。
2. 再次请求 `tools/list`，确认工具消失。
3. 直接构造 `tools/call`，确认调用仍会被拒绝。

这个反向测试比只展示成功调用更有说服力，因为它能证明权限不是只控制页面显示。

## 九、项目亮点怎么讲

### 亮点一：在协议层解决框架的静态能力限制

Spring AI 擅长注册固定的内置 Tool，但企业平台希望在线新增 Tool、Prompt 和 Resource。项目选择在标准 MCP 消息层完成鉴权、能力注入、响应改写和动态分发，使运行能力不完全受框架启动时的固定集合限制。

面试表达：

> 我没有把平台绑死在某个 SDK 内部，而是利用 MCP 基于 JSON-RPC 的开放边界扩展能力。固定能力仍交给框架，动态能力由平台治理和分发，这样保留了框架成熟的协议处理，又实现了运行期扩展。

### 亮点二：工具从代码变成可治理的数据资产

传统 Tool 的变化路径是“改代码 -> 测试 -> 发版 -> 重启”。动态 Tool 的变化路径是“创作 -> 调试 -> 发布 -> 授权 -> 使用”。

价值：

- 缩短简单业务工具的交付周期。
- 让业务 API 可以被重新组合，而不是重复开发。
- 支持草稿、私有发布、公开发布和下线。
- 让工具具备统一的描述、参数、权限、审计和生命周期。

### 亮点三：角色权限和 Token 选择的双层模型

```text
最终可用能力 = 角色授权上限 ∩ Token 实际选择
```

第一层解决安全问题，第二层不仅解决场景隔离，还解决 LLM 上下文预算问题。因为工具列表会进入模型上下文，工具越多，Token 成本越高，语义相似工具越容易误选。

面试表达：

> RBAC 回答用户最多能做什么，Token 选择回答某个客户端这次需要携带什么。第二层不是重复授权，而是 Agent 场景下的最小暴露和上下文预算管理。

### 亮点四：动态工具不是任意联网，而是白名单编排

动态 Tool 不能任意访问所有企业接口和数据源，只能调用发布时明确绑定的 API Key 和数据源 ID。这样权限不是一句“脚本安全”，而是细化到某个工具具体能使用哪些能力。

### 亮点五：完整覆盖能力生命周期

```text
创作 -> 调试 -> 保存 -> 发布 -> 社区发现
     -> 角色授权 -> Token 选择 -> MCP 调用 -> 审计 -> 下线
```

很多项目只展示“工具能调用”，Bear MCP 还覆盖了能力如何被生产、治理、复用和追踪。

### 亮点六：Tool、Prompt、Resource、Skill 协同

项目没有把所有内容都塞进 Tool：事实放 Resource，本次任务要求放 Prompt，长期工作方法放 Skill，真实动作交给 Tool。这样知识、流程和执行边界更清楚，也更方便单独更新和授权。

### 亮点七：Agent 自扩展闭环

平台提供创建 API、创建 Tool、创建 Prompt、创建 Resource、创建 Skill 等元能力。由于能力本身已经数据化，Agent 可以在授权范围内帮助创建新的能力草稿，再由人审核发布。

```text
人提出需求
    -> Agent 创建能力草稿
    -> 人调试和审核
    -> 发布并授权
    -> Agent 在下一次会话中使用新能力
```

面试时一定要强调“人审发布”，不要把它说成 Agent 可以不受控地执行任意代码。

### 亮点八：Text-to-SQL 做的是企业语义治理

项目没有只写一个“根据问题生成 SQL”的 Prompt，而是拆成：

- Schema Resource：表、字段、关联和安全标记。
- Business Resource：业务词、状态和对象含义。
- Metrics Resource：指标公式、主表、时间字段和维度。
- Prompt：本次查询参数、输出格式和澄清规则。
- Skill：长期工作步骤和资源选择方法。
- Tool：只读执行 SQL。

面试表达：

> Text-to-SQL 的难点不是 SQL 语法，而是业务语义。销售额按哪个状态、哪个金额字段、哪个时间字段计算，模型不应该猜，必须由企业指标资源明确提供。

### 亮点九：成功和失败都可审计

审计不仅记录成功调用，还要记录拒绝、异常和耗时。这样平台能回答：谁、何时、使用哪把 Token、调用哪个能力、是否成功、花了多久。

## 十四、高频追问与回答

### Q1：为什么不用普通 REST API？

> REST API 解决系统之间怎么请求，MCP 还规定 Agent 如何发现能力、理解参数并标准化调用。Bear MCP 不是替代 REST，而是把已有 REST API 治理后封装成 Agent 能理解的 MCP 能力。

### Q2：为什么不直接让 Agent 连接数据库？

> 直接连接会扩大权限和误操作风险，也很难统一做字段限制、结果上限和审计。项目只给 Agent 暴露受控的只读查询能力，并要求数据源白名单、只读 SQL 和结果上限。

### Q3：为什么角色授权后还要 Token 选择？

> 角色决定用户的能力上限，Token 决定某个客户端这次实际装载哪些能力。对 Agent 来说，工具列表会进入上下文，最小装载可以降低成本和误选率，所以第二层既是安全隔离，也是上下文预算管理。

### Q4：动态 Tool 和固定 Tool 有什么区别？

> 固定 Tool 适合稳定、核心、对性能和类型安全要求高的能力；动态 Tool 适合快速变化、主要做 API 或数据源编排的业务能力。两者不是互相替代，而是分别覆盖稳定能力和快速迭代能力。

### Q5：Groovy 安全吗？

> 当前做了危险行为校验、受限能力注入、API 与数据源白名单、线程池和超时，但黑名单沙箱不能等价于强安全隔离。当前定位是内部受信创作者和防误操作；生产环境应进一步采用白名单语法、独立进程或容器隔离、网络出站策略和更严格的资源限制。

### Q6：社区里看到一个 Tool，是不是就能调用？

> 不是。公开只代表可发现，调用仍然需要角色授权和 Token 选择。项目刻意把“公开展示”和“运行权限”分开。

### Q7：Text-to-SQL 的最大价值是什么？

> 不是生成 SQL，而是把表结构、业务术语、指标口径、执行规则和权限统一治理。模型生成的 SQL 看起来正确不代表业务口径正确，企业语义资产才是可靠性的基础。

### Q8：项目最有技术含量的地方是什么？

> 第一是利用 MCP 协议边界扩展框架的静态能力；第二是双层权限背后的上下文预算设计；第三是能力数据化以后形成的 Agent 辅助创作和人审发布闭环。

### Q9：你怎么证明权限有效？

> 我会做正反两组测试：授权并选择后，能力在列表中出现且可以调用；取消 Token 选择后，列表中消失，而且直接构造调用仍被拒绝。最后查看拒绝审计，证明不是只改了页面展示。

### Q10：如果有十万个 Tool 怎么办？

> 十万个 Tool 全量进入上下文本身就不成立。需要按领域分层发现，或者根据当前问题先做工具语义检索，只向模型暴露 Top-K 候选工具。

## 十五、项目不足与生产化改进

主动讲不足会比等面试官挖出来更有说服力。

### P0：生产前必须解决

1. 数据库凭据和 JWT 密钥不能写在项目配置中，应迁移到环境变量或配置中心并立即轮换。
2. 后台不仅要认证，还需要真正的接口级授权和资源归属校验。
3. 动态 Tool、API、Prompt、Resource、Skill 都要完善创建者归属和修改权限。
4. 外部 HTTP 调用需要域名白名单、内网网段拦截、DNS 重绑定防护和参数转义，防止 SSRF。
5. 动态脚本需要从黑名单升级到白名单，并逐步迁移到独立进程或容器隔离。

### P1：稳定性与性能

1. 脚本按内容哈希做编译缓存，避免重复编译。
2. 超时后要取消任务，并增加线程池隔离、熔断和拒绝策略。
3. Token 权限上下文做短 TTL 缓存，权限变化时主动失效。
4. 审计改为异步队列和批量写入。
5. 限流从单机内存升级为带 TTL 的本地缓存或 Redis 分布式限流。
6. SQL 使用解析器做白名单校验，并设置数据库连接只读、最大行数和查询超时。
7. 前端进行路由和按需加载，降低当前较大的主包体积。

### P2：工程质量

1. 补 MCP 核心链路集成测试和权限矩阵测试。
2. 增加 Testcontainers 或独立测试库，保证数据库测试可重复。
3. 接入 OpenTelemetry，把一次用户请求与多次能力调用串成 Trace。
4. 日志降敏，避免记录 Token、Authorization、SQL 敏感参数和完整请求体。
5. 建立能力版本、灰度发布、回滚和调用成功率对比。

面试话术：

> 当前版本证明了架构和产品闭环，但我不会把教学版本包装成已经可直接生产上线。生产化最先处理密钥、授权、资源归属和执行隔离，然后补核心链路测试、缓存、异步审计和可观测性。

2. **双层权限**：角色管上限，Token 管本次装载和上下文预算。
3. **能力闭环**：创作、调试、发布、授权、调用、审计和下线。

### 五类资产

```text
Tool：动作
Prompt：本次任务模板
Resource：只读事实
Skill：长期方法
API 配置：企业接口积木
```

### 一条完整链路

```text
企业 API / 数据库 / 文档
    -> 平台创作和治理
    -> 发布
    -> 角色授权
    -> Token 选择
    -> MCP Client 发现
    -> Agent 调用
    -> 审计追踪
```

### 三个必须主动承认的不足

```text
配置和密钥管理仍需生产化
Groovy 沙箱不是强安全隔离
核心 MCP 权限与动态分发测试覆盖不足
```

### 最短应急版

> Bear MCP 是一个企业 AI 能力中台，把 API、数据库、知识和流程统一封装成 MCP 能力。项目支持动态 Tool、Prompt、Resource、Skill、双层权限、创作发布、社区复用和调用审计。最大亮点是利用 MCP 协议边界实现运行期动态能力，并用角色权限加 Token 选择同时解决安全和模型上下文预算问题。

### 收尾句

> 这个项目让我认识到，企业 Agent 的难点不只是让模型会调用工具，而是让能力能够被标准化生产、最小化授权、可靠地运行，并在出问题时可以追踪和治理。
